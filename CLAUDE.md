# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A multipart FIJI/ImageJ plugin (Maven, `pom-scijava` parent) for analyzing two-channel single-molecule FRET (smFRET) microscopy data. Three SciJava `Command` plugins are meant to be run in sequence, each consuming the previous step's output file(s):

1. **smFRETChannelMapper** (`smFRETChannelMapper.java`) — computes an affine mapping between the donor/target (left half of the image) and acceptor/source (right half) channels using TurboReg landmark registration on an averaged image. Outputs `<name>_mapping.json` (affine transform + expected image size) and a QC overlay TIF.
2. **smFRETSpotFinder** (`smFRETSpotFinder.java`) — loads the mapping JSON, finds candidate spots (local maxima) in the averaged, channel-summed image, then filters them by edge proximity, inter-spot proximity, SNR, and prominence. Outputs `<name>_spotf_finding.json` (parameters + file references), `<name>_spotf_spots.csv` (surviving spot table), `<name>_spotf_qc_image.tif`, and `<name>_spotf_masks.tif` (overlap mask + background mask as a 2-frame stack).
3. **smFRETAnalyzer** (`smFRETAnalyzer.java`) — loads the spot-finder JSON, re-derives the mapping/masks/spot list from it, estimates a per-frame background via temporal boxcar filtering, and measures per-spot donor/acceptor time traces. Outputs `<name>.h5` (metadata, spot table, target/source trace matrices) and `<name>.traces` (Taekjip Ha lab binary format).

Each of those three `run()` methods derives a `saveRootName` from its primary input file path (strips the extension) and writes all outputs alongside the input using that root. See `README.md` for the full parameter/output reference exposed to end users in the ImageJ UI.

A fourth plugin sits outside that chain:

4. **smFRETTraceHistogram** (`smFRETTraceHistogram.java`) — an interactive viewer for the `.h5` written by stage 3. It is the only plugin here that builds its own Swing UI rather than relying on SciJava's generated parameter dialog, and the only one that writes nothing unless the user clicks Save. It reads just `target-traces` and `source-traces` from the H5 — deliberately not `spots` or `spots-fields`, which are absent from files written before `d99e74a`. Each trace contributes **one** point (its mean over the selected frame interval), not one per frame, and the FRET value is the ratio of the averaged intensities `mean(A)/(mean(D)+mean(A))` rather than the mean of the per-frame ratios — the two differ substantially (~0.2 in the mean on the example data). The intensity threshold is an all-frames test — a trace is excluded if *any* frame in the interval falls below it, not if its average does — which makes it far stricter than it looks (on the example data any threshold ≥ 0 empties the histogram). The threshold slider's bounds come from per-frame min/max rather than from the trace averages, which is what guarantees its low end can never silently exclude a trace. `computeHistogram` deliberately takes its settings as arguments rather than reading the Swing controls, so the binning can be exercised without a display. The frame interval is picked with `RangeSlider`, a hand-rolled two-handle slider (Swing has none) whose bar can be dragged to move a fixed-width window through the movie — it enforces `low <= high` internally, which is why `update()` has no crossover handling. Because a track is only a few hundred pixels wide, the mouse cannot address every frame of a long movie; the arrow keys move the window one frame at a time and are the only way to land on an exact interval.

## Architecture notes

- **Composition, not shared base class.** `smFRETSpotFinder` owns a private `smFRETChannelMapper` instance (`smfcm`) and `smFRETAnalyzer` owns a private `smFRETSpotFinder` instance (`smfsf`). Downstream plugins call into the upstream plugin's public methods (`splitImagePlus`, `loadMappingJSON`, `backgroundEstimate`, etc.) directly on these instances rather than through interfaces. When changing a method signature in one class, check both downstream classes for direct callers.
- **Two-channel image convention.** Every FRET stack is a single image whose left half is the donor/target channel and right half is the acceptor/source channel. `splitImagePlus` (in `smFRETChannelMapper`) is the canonical way to split and optionally TurboReg-transform the source half onto the target half's coordinate frame; both other classes call it rather than re-implementing the split.
- **The channel sum is float, and results before that change are not comparable.** `smFRETSpotFinder.run()` adds the two halves to make the image everything downstream is measured from. That was `ImageCalculator.run(target, source, "add create")`, which takes its result type from the *first* operand — the 8-bit target half — and ImageJ1's 16→8-bit conversion **scales by the display range**. On the example data the acceptor half spanned 0–50 and so was stretched to 0–255: a **5.1× amplification of the acceptor relative to the donor**, then saturated at 255 (mean 103.9 against a true 35.9). The factor is whatever that movie's source-half range happens to be, so it differed from movie to movie and no two were weighted alike. The sum is now computed in float with `LoopBuilder`, both channels at equal weight. **Consequence: `spotThreshold`, `spotProminence` and `spotTolerance` were tuned against the amplified image and need re-deriving.** Median SNR fell 15.1 → 10.0 on `hel1` once the acceptor stopped being amplified, and the spot set changed by more than its count did — 461 → ~425 spots with only 86% of the new ones within a pixel of an old one. A `spotTolerance` sweep from 1.5 to 10 moved the count only between 390 and 427 (plateau 3–7, non-monotonic because more maxima means more pairs culled by the proximity filter), so tolerance is not the binding constraint; the SNR and prominence filters are.
- **The temporal average is a plain boxcar now, and the spatial part it used to carry was measured out rather than dropped on taste.** `backGroundEstimation` called `Filters3D.filter(stack, MEAN, 1, 1, N)`, whose x/y radius of 1 averaged spatially too — its neighbourhood matched neither a 3×3×(2N+1) box nor a pure temporal window (1.53 and 1.17 ADU off, on values around 19). It is now a running-sum temporal mean over `RandomAccessibleInterval`, one pass over the movie, with the window **shrinking at the ends instead of extrapolating** — the other thing the old `FIXME` worried about. `backgroundAverageNFrames` is now the **whole window**, matching what the README always said it was; `Filters3D` took it as a z *radius*, so 30 meant 61 frames. On a 30-frame movie that bug made the window cover the entire movie for every frame, and the background estimate came out **identical on every frame** (frame-to-frame spread exactly 0) — it could not track lamp drift or anything else time-varying. With the fix it varies by 1.7 ADU frame to frame, and the post-bleach donor level moves from −58 to +32: nearer zero in magnitude, but now under-subtracting where it used to over-subtract. Putting a 3×3 spatial average back was tried and made the post-bleach donor level worse (−58 → −62), so it stays out.
- **Swapping `blurGaussian` for `Gauss3` moved the background by ~0.6 ADU, and the clip threshold was calibrated against the old kernel.** Spot detection barely noticed — identical maxima and identical counts through the SNR filter, one extra spot after prominence, SNR shifted 0.14% — but traces moved by ~25 units on a mean |trace| of 167, because the background estimate sits ~0.6 ADU higher. The post-bleach donor level, which should be zero, went from −42 to −58. imglib2's kernel is the more principled one (ImageJ1 downscales its kernel above σ≈2, which is where the 3.9% divergence at σ=14 comes from), but `backgroundKappa`'s `1.5 − 0.3·spotSigma` was swept against ImageJ1's blur. **Re-deriving κ against the current smoothing is outstanding work**, and is the same re-calibration the float channel sum already asked for.
- **The stack axis cannot be checked, only the cases where there is more than one.** ImageJ gives a movie and a depth stack identical dimensions when either is saved as a plain TIFF — the example data reports **z=30, t=1**, and so does a genuine 30-slice volume. There is no flag to read, so `requireTimeStack` cannot demand t>1 without refusing every movie the plugin has ever run on; a stack with one non-singleton axis is taken as a time series, which is what the pipeline assumed all along. What it does refuse is anything with two: z>1 **and** t>1 is a real 4D acquisition with no answer to which axis to walk, and more than one channel means the two FRET channels are stored separately rather than side by side within each frame. `frameCount` reads `getStackSize()` rather than `getNSlices()`, which is what makes a stack saved with t=30, z=1 work — that used to average nothing and analyse frame 1 alone.
- **Input images are guarded, and the image type alone is not the test.** `smFRETChannelMapper.requireGrayscale` runs at all three `run()` entry points and blocks anything that is not 8, 16 or 32 bit grayscale, because every stage assumes one number per pixel. RGB is caught by `getType()`, but a colour-indexed PNG or GIF opens through `ImagePlus` as **GRAY8, not COLOR_256** — verified against files written for the test — so 8-bit images are additionally required to have no colour lookup table. That test is deliberately not applied above 8 bits, where a colour LUT is display-only over real intensities. The cost is that an 8-bit image carrying a display LUT is refused even though its values are fine; that direction is recoverable (the message names the fix) whereas the other silently measures palette indices.
- **Widen to double before subtracting.** ImageJ1's `ImageProcessor.getValue` returns a double, so arithmetic written against it was double arithmetic. Reading an imglib2 `float[]` directly and subtracting gives *float* arithmetic, which moved the traces by 1e-4 — nothing against the signal, but not nothing. The same trap cost 1 ADU on 5 pixels per million in the channel mapper's interpolation, where the fix was a `DoubleType` converter view. Anywhere ImageJ1 accumulated in double and imglib2 would accumulate in float, widen deliberately.
- **The spot finder is imglib2 except for three islands.** The arithmetic, masks, filters and background estimator are `LoopBuilder` over `RandomAccessibleInterval`, and the smoothing is `Gauss3`. What stays ImageJ1: `MaximumFinder`, whose tolerance-based flood fill has no imglib2 equivalent (`LocalExtrema` is a strict neighbourhood test); the ROI rasterizers, where `fillOval` covers 69 pixels at radius 4 against 49 for the analytic disc, so the mask footprint would change; and `ResultsTable`/`FileSaver`, which are I/O rather than pixels. The `Shared` class holds one `float[]` viewed as both an `ArrayImg` and a `FloatProcessor` so the islands run in place with no conversion.
- **Mask conventions in `smFRETSpotFinder`:** `overlapMask` marks pixels inside the valid overlap region of both channels (used to drop spots near channel edges); `backgroundMask` marks pixels not within `spotMargin` of any spot, which is a fixed 4 rather than a parameter — sweeping it found anything from 2 to 6 within 11% of the best at any spot size, because the estimator clips rather than trusting the mask. Both are persisted together as a 2-frame TIF (`_spotf_masks.tif`) and reloaded via `loadMasks()`.
- **Background estimation is sigma-clipped normalized convolution.** `backgroundEstimate(image)` smooths the image and the trusted mask with the same Gaussian and divides one by the other, which fills the spots *and* the edges in one pass; then it drops pixels sitting more than a threshold of MAD-based standard deviations **above** that estimate and repeats, four rounds. The clipping is one-sided on purpose — contamination only ever brightens a pixel. There is no seeded second flavor: it converges in a fixed few rounds with nothing to carry over between frames, so `smFRETAnalyzer.backGroundEstimation()` estimates each frame independently — and reads neither `spotMargin` nor `edgeMargin`, which is why it no longer sets them on `smfsf`. It replaced an iterated Gaussian inpaint that trusted `backgroundMask` completely; on the example long movie that inpaint drove two thirds of photobleached traces significantly below zero (median −23 photoelectrons), because a real PSF's wings reach past any masking radius a crowded field can afford and the estimator read the background high exactly where it was about to be subtracted.
- **Only one of the three background settings follows the spot size, and it is not the geometric one.** All three were swept together against a known background over simulated aberrated Airy PSFs from sigma 1 to 3. The **masking radius** barely matters — 2 to 6 pixels are within 11% of each other at every sigma, 4 within 2% — because the clip finds contaminated pixels itself, so `spotMargin` is a fixed 4 and not a parameter. The **smoothing scale** showed no trend against sigma at all (fit 14.4 − 0.00·σ) and is a constant 14; it was `2 * spotMargin`, i.e. 8, which costs 40–60% more error than 14 at every sigma above 1. The **clipping threshold** is the sharp one, 15–40% for one grid step, and is derived as `1.5 − 0.3 * spotSigma` by `clippingThreshold()`. It *falls* with spot size because a wider PSF spreads the same wing photons over more pixels, so contamination is a smaller per-pixel excursion. `backgroundKappa` overrides it when set above 0, and that hatch exists for a live conflict: the formula gives 0.93 at the example long movie's `spotsigma` of 2.0, where measuring on that movie directly gave 1.8 — its PSF actually fits at 1.36, and its illumination may have structure the simulation's smooth Gaussian beam lacks. The effective value is written to the spot-finder JSON as `"background kappa"`; files written before this lack the key and the reader falls back.
- **Spot arrays are `double[][]` shaped `[spot][field]`, and there are two incompatible layouts — check which one you're holding.**
  - *In memory during spot finding:* column 0 is a boolean-as-double "is this spot still good" flag written by each filter stage (`spotFilterWithMask`, `spotFilterSNR`, `spotFilterProminence`), so x/y live at columns 1/2. `getMaxima` returns width 3 (`flag, x, y`); `spotFilterSNR` appends SNR (width 4); `spotFilterProminence` appends prominence (width 5). Filters append a diagnostic column rather than overwriting existing ones.
  - *After a save/load round-trip:* the flag is gone. `saveSpotLocations` writes only good spots starting from index `j+1`, and `loadSpotLocations` reads back into index `j`, so the reloaded array is `x, y, snr, prominence` with **x at column 0** (matching `columnHeaders`).
  - `smFRETAnalyzer` only ever sees the reloaded form — hence `spots[j][0]`/`spots[j][1]` as x/y in `measureTimeTraces` — while everything inside `smFRETSpotFinder` uses the flag-prefixed form. The round trip only lines up because exactly two widening filters run and `columnHeaders.size() == 4`; adding a filter stage means updating `columnHeaders` in lockstep.
- **JSON as the inter-plugin contract.** Jackson `ObjectMapper` reads/writes plain `Map<String,Object>` (via `HashMap.class`), not typed DTOs. Downstream plugins read specific keys by string (e.g. `smFRETAnalyzer.run()` pulls `"root name"`, `"image name"`, `"mapping file"`, `"masks file"`, `"spots file"`, `"spot sigma"`, `"camera black"`, `"camera gain"` out of the spot-finder JSON) and must stay in sync with the keys the upstream plugin writes.
- **Menu registration is deliberately doubled.** Each command carries a SciJava `@Plugin(menu = {@Menu(...)})` declaration *and* an entry in `src/main/resources/plugins.config`. The annotations alone place the `smFRET` submenu in the trailing section of Fiji's Plugins menu (after the separator that follows `Volume Viewer`), because that is where `imagej-legacy` appends ImageJ2 commands — and no `@Menu` weight can move it across that separator (verified empirically). The `plugins.config` entries put it in the main plugins section instead. Consequences: **in Fiji the order of lines in `plugins.config` determines the order of items inside the submenu, and the `@Menu` weights do not** — they only apply where the legacy layer isn't involved. The listed classes are `Command`s rather than `ij.plugin.PlugIn`s; Fiji's legacy patcher dispatches them into the SciJava command service regardless, so parameter dialogs still work.
- **TurboReg measures mappings; imglib2 applies them.** TurboReg is called via reflection (`IJ.runPlugIn("TurboReg_", options)` + `getClass().getMethod(...)`) because it isn't a compile-time Maven dependency — it must be installed separately into the Fiji/ImageJ plugins directory at runtime. It is used for **`-align` only**, in `smFRETChannelMapper.run()`, which is the one thing it does that nothing else here can: fit an affine to two images. Applying a known affine is `transformImagePlus`, which solves the affine from the three landmark pairs in `loadMappingJSON` into an `AffineTransform2D` and samples an `NLinearInterpolator` in memory — no temp file, no reflection, and testable without a Fiji install. It runs once per frame per channel from both `smFRETAnalyzer` stages, so it is the hot path; TurboReg's `-transform` took 6.9 ms on 256×512 against 1.4 ms here, and only 0.5 ms of that was the temporary file.
- **The warp is n-linear where TurboReg's was a cubic spline, and that is fine — measured, not assumed.** On the example mapping and data: geometry agrees to 0.003 px of spot centroid (the affine is exactly determined by three point pairs, so this is arithmetic, not luck); stored 16-bit values differ for 14% of pixels, 14.17% of them by exactly 1 ADU and 0.12% by ≥2; per-spot intensities after the smoothing that precedes trace measurement differ by a median of 0.45% (p95 0.75%). The decisive number is that rounding into 16 bit at the end of `transformImagePlus` has an rms error of 0.26 ADU against 0.24 ADU between the two interpolators — **storing the image perturbs it more than the choice of interpolator does**. Higher-order interpolation is not worth buying back: imglib2 Lanczos halves the pixel-level difference but is no closer on per-spot intensity, because the σ=2 smoothing discards the difference, and it is 6× slower than TurboReg. Two details are load-bearing and were each worth a measurement: the out-of-range test is on the **inverse-mapped coordinate** rather than the sampled value, which is what `createOverlapMask` relies on and what keeps a 3 px band around the frame from shifting by up to 19 ADU; and the interpolation runs through a `DoubleType` view because ImageJ1 interpolated in double, and matching that is worth 1 ADU on ~5 pixels per million.
- **Diagnostic mode:** each class has a `private final boolean diagnostic_mode = true` field controlling whether intermediate images (averages, smoothed foreground/background, per-frame background stacks) are written to disk alongside the primary outputs. There's no CLI flag for this — toggle the field directly when debugging.
- Exceptions specific to this plugin's own validation (e.g. image-size mismatches against a loaded mapping) are raised as `smFRETAnalysisException` (unchecked). Everything else is caught broadly in each `run()` and routed to `log.info(e)` + `IJ.handleException(e)` rather than propagated, since these are top-level SciJava commands.

## Build

Maven build against the `pom-scijava` BOM/parent, **which must run on a JDK that can still emit Java 8 bytecode**:

```
JAVA_HOME=/usr/lib/jvm/java-11-openjdk-amd64 mvn clean package
```

`pom-scijava` sets `maven.compiler.release` to 8 (matching the Java 8 runtime Fiji bundles — `Fiji.app/java/zulu8*`), and the JDK 21 compiler rejects `--release 8` with `error: release version 8 not supported`. Plain `mvn clean package` therefore fails on a machine whose default `java` is 21: `maven-compiler-plugin` compiles in-process using the compiler of whichever JVM Maven itself is running on, so it is `JAVA_HOME`/`java` that decides, **not** the `javac` on `PATH` — a PATH `javac` of 11 does not rescue the build. `mvn -version` reports the JVM actually in use. Add `-o` to build offline once the dependencies are in `~/.m2`.

The build resolves ImageJ/SciJava core artifacts from Maven Central plus the `scijava.public` repository declared in `pom.xml`. There is no test suite in this repository (no `src/test`), so `mvn test`/`mvn verify` runs no tests.

**Runtime dependency not in `pom.xml`:** the channel mapper requires the [TurboReg](https://imagej.net/plugins/turboreg) plugin (v2.0.1) to be present in the target Fiji/ImageJ installation's plugin path — it's invoked via reflection at runtime, not linked at compile time.

To use the plugin, install the built jar into a Fiji/ImageJ `plugins/` directory alongside TurboReg; the four commands then appear under `Plugins > smFRET`.
