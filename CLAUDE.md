# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A multipart FIJI/ImageJ plugin (Maven, `pom-scijava` parent) for analyzing two-channel single-molecule FRET (smFRET) microscopy data. Three SciJava `Command` plugins are meant to be run in sequence, each consuming the previous step's output file(s):

1. **smFRETChannelMapper** (`smFRETChannelMapper.java`) — computes an affine mapping between the donor/target (left half of the image) and acceptor/source (right half) channels using TurboReg landmark registration on an averaged image. Outputs `<name>_mapping.json` (affine transform + expected image size) and a QC overlay TIF.
2. **smFRETSpotFinder** (`smFRETSpotFinder.java`) — loads the mapping JSON, finds candidate spots (local maxima) in the averaged image — the channel sum by default, or either channel alone via `spotChannel` — then filters them by edge proximity, inter-spot proximity, SNR, and prominence. Outputs `<name>_spotf_finding.json` (parameters + file references), `<name>_spotf_spots.csv` (surviving spot table), `<name>_spotf_qc_image.tif`, and `<name>_spotf_masks.tif` (overlap mask + background mask as a 2-frame stack).
3. **smFRETAnalyzer** (`smFRETAnalyzer.java`) — loads the spot-finder JSON, re-derives the mapping/masks/spot list from it, estimates a per-frame background via temporal boxcar filtering, and measures per-spot donor/acceptor time traces. Outputs `<name>.h5` (metadata, spot table, target/source trace matrices) and `<name>.traces` (Taekjip Ha lab binary format).

Each of those three `run()` methods derives a `saveRootName` from its primary input file path (strips the extension) and writes all outputs alongside the input using that root. See `README.md` for the full parameter/output reference exposed to end users in the ImageJ UI.

Two further plugins sit outside that chain:

4. **smFRETTraceHistogram** (`smFRETTraceHistogram.java`) — an interactive viewer for the `.h5` written by stage 3. It is the only plugin here that builds its own Swing UI rather than relying on SciJava's generated parameter dialog, and the only one that writes nothing unless the user clicks Save. It reads just `target-traces` and `source-traces` from the H5 — deliberately not `spots` or `spots-fields`, which are absent from files written before `d99e74a`. Each trace contributes **one** point (its mean over the selected frame interval), not one per frame, and the FRET value is the ratio of the averaged intensities `mean(A)/(mean(D)+mean(A))` rather than the mean of the per-frame ratios — the two differ substantially (~0.2 in the mean on the example data). The intensity filter is a **range**, min and max, and both ends are an all-frames test — a trace is excluded if *any* frame in the interval falls outside it, not if its average does — which makes it far stricter than it looks (on the example data any minimum ≥ 0 empties the histogram). The max is deliberately symmetric: one bright frame drops a trace, which is what catches an aggregate but also catches a single spike. Its bounds come from per-frame min/max rather than from the trace averages, which is what guarantees neither end can silently exclude a trace while parked at its extreme. `computeHistogram` deliberately takes its settings as arguments rather than reading the Swing controls, so the binning can be exercised without a display. Both the frame interval and the intensity range are picked with `RangeSlider`, a hand-rolled two-handle slider (Swing has none) whose bar can be dragged to move a fixed-width window through the movie — it enforces `low <= high` internally, which is why `update()` has no crossover handling. Because a track is only a few hundred pixels wide, the mouse cannot address every frame of a long movie; the arrow keys move the window one frame at a time and are the only way to land on an exact interval. Three spin boxes carry per-frame corrections — a donor baseline, an acceptor baseline and a donor-into-acceptor leakage fraction — grouped into a `Corrections` value class rather than three more doubles on a signature that already took seven. Both baselines are **subtracted**, and leakage comes off the acceptor using the **baseline-corrected** donor, since leakage is a fraction of real donor emission and a residual offset is not. They are applied inline in `computeHistogram` rather than into a second pair of trace arrays — three flops per frame per spot against doubling trace memory on a long movie. The load-bearing consequence is that `computeFilterBounds` — the per-frame min/max that sets the Range slider's limits — **has to be redone whenever a correction changes**, and the slider rescaled and reopened: the bounds are what guarantees an end parked at its extreme excludes nothing, and subtracting a baseline moves the data out from under bounds taken on the raw traces. Verified against an independent implementation of the same arithmetic over seven correction settings × four histogram types, agreeing to 1e-13; two internal checks fall out of it, that leakage 1.0 makes the total histogram exactly the uncorrected acceptor (`D + (A − D) = A`) and that a leakage of 0.08 moves the acceptor mean by 0.08 × the donor mean. Setting all three back to zero restores the original bounds exactly.

5. **smFRETTraceVisualizer** (`smFRETTraceVisualizer.java`) — one spot at a time, in **two** windows: the field, which is where a spot is picked, and a second window holding everything that follows from the pick — the traces on top, and the donor and acceptor images at a slider-chosen frame side by side below, split so either half can be given the space (`setResizeWeight(1.0)` sends extra height to the traces, since the images are square and stop gaining from it). Closing either window disposes both; neither is usable alone, as the field has nothing to report a selection to and the traces have no way to change which spot they show. The field stays separate because it is 256×512 and picking one spot out of a crowded field needs it drawn large. Interactive, writes nothing. Its input is the **spot-finder JSON**, and the link that makes the whole thing work is that `measureTimeTraces` walks the spot table in load order, so **trace row `j` is spot-table row `j`** — a mismatch in length means the `.h5` and the CSV are from different runs and every trace would be attributed to the wrong spot, which is checked on load. The root name comes from the **JSON's own path** minus `_spotf_finding.json`, not from the `"root name"` key: that key is recorded relative to whatever directory stage 2 ran in (`mnew/hel1`), so it does not survive being opened from anywhere else, and `<root>.h5` / `<root>_spotf_qc_image.tif` hang off it. Frames are split and warped **one at a time on demand** and cached singly, rather than the movie being converted to float up front the way stage 3 does it — a viewer that did that would want gigabytes to show one spot. Window 1 shows the QC image rather than a movie frame because a single frame of an 8-bit movie is noisy enough that most spots are invisible in it; this is also why the crop-centring check has to be done on frame-*averaged* crops, where the peak lands within 1.5 px of centre for 95.8% of donor and 93.0% of acceptor crops on `hel1` (the acceptor is exactly centred less often — 52.0% against 69.6% — because spots are found in the sum image and the acceptor half is warped). The two zoom windows share **one display range measured over the whole movie from both channels**, sampled from up to 48 frames since each sample costs a split and a warp; per-frame autoscaling would normalize away the bleaching that is the main thing worth looking at.

## Architecture notes

- **Composition, not shared base class.** `smFRETSpotFinder` owns a private `smFRETChannelMapper` instance (`smfcm`) and `smFRETAnalyzer` owns a private `smFRETSpotFinder` instance (`smfsf`). Downstream plugins call into the upstream plugin's public methods (`splitImagePlus`, `loadMappingJSON`, `backgroundEstimate`, etc.) directly on these instances rather than through interfaces. When changing a method signature in one class, check both downstream classes for direct callers.
- **Two-channel image convention.** Every FRET stack is a single image whose left half is the donor/target channel and right half is the acceptor/source channel. `splitImagePlus` (in `smFRETChannelMapper`) is the canonical way to split and optionally TurboReg-transform the source half onto the target half's coordinate frame; both other classes call it rather than re-implementing the split.
- **The channel sum is float, and results before that change are not comparable.** `smFRETSpotFinder.run()` adds the two halves to make the image everything downstream is measured from. That was `ImageCalculator.run(target, source, "add create")`, which takes its result type from the *first* operand — the 8-bit target half — and ImageJ1's 16→8-bit conversion **scales by the display range**. On the example data the acceptor half spanned 0–50 and so was stretched to 0–255: a **5.1× amplification of the acceptor relative to the donor**, then saturated at 255 (mean 103.9 against a true 35.9). The factor is whatever that movie's source-half range happens to be, so it differed from movie to movie and no two were weighted alike. The sum is now computed in float with `LoopBuilder`, both channels at equal weight. **Consequence: `spotThreshold`, `spotProminence` and `spotTolerance` were tuned against the amplified image.** All three have since been re-derived, along with `backgroundKappa` and `spotMargin`. Median SNR fell 15.1 → 10.0 on `hel1` once the acceptor stopped being amplified, and the spot set changed by more than its count did — 461 → ~425 spots with only 86% of the new ones within a pixel of an old one.
- **The temporal average is a plain boxcar now, and the spatial part it used to carry was measured out rather than dropped on taste.** `backGroundEstimation` called `Filters3D.filter(stack, MEAN, 1, 1, N)`, whose x/y radius of 1 averaged spatially too — its neighbourhood matched neither a 3×3×(2N+1) box nor a pure temporal window (1.53 and 1.17 ADU off, on values around 19). It is now a running-sum temporal mean over `RandomAccessibleInterval`, one pass over the movie, with the window **shrinking at the ends instead of extrapolating** — the other thing the old `FIXME` worried about. `backgroundAverageNFrames` is now the **whole window**, matching what the README always said it was; `Filters3D` took it as a z *radius*, so 30 meant 61 frames. On a 30-frame movie that bug made the window cover the entire movie for every frame, and the background estimate came out **identical on every frame** (frame-to-frame spread exactly 0) — it could not track lamp drift or anything else time-varying. With the fix it varies by 1.7 ADU frame to frame, and the dark-frame donor level moves from −58 to +32: nearer zero in magnitude, but now under-subtracting where it used to over-subtract. Putting a 3×3 spatial average back was tried and made the dark-frame donor level worse (−58 → −62), so it stays out.
- **Swapping `blurGaussian` for `Gauss3` moved the background by ~0.6 ADU, and the clip threshold was calibrated against the old kernel.** Spot detection barely noticed — identical maxima and identical counts through the SNR filter, one extra spot after prominence, SNR shifted 0.14% — but traces moved by ~25 units on a mean |trace| of 167, because the background estimate sits ~0.6 ADU higher. The dark-frame donor level, which should be zero, went from −42 to −58. imglib2's kernel is the more principled one (ImageJ1 downscales its kernel above σ≈2, which is where the 3.9% divergence at σ=14 comes from), and `backgroundKappa` has since been re-derived against the current smoothing — it is a constant 1.3 now, not a function of `spotSigma`.
- **The stack axis cannot be checked, only the cases where there is more than one.** ImageJ gives a movie and a depth stack identical dimensions when either is saved as a plain TIFF — the example data reports **z=30, t=1**, and so does a genuine 30-slice volume. There is no flag to read, so `requireTimeStack` cannot demand t>1 without refusing every movie the plugin has ever run on; a stack with one non-singleton axis is taken as a time series, which is what the pipeline assumed all along. What it does refuse is anything with two: z>1 **and** t>1 is a real 4D acquisition with no answer to which axis to walk, and more than one channel means the two FRET channels are stored separately rather than side by side within each frame. `frameCount` reads `getStackSize()` rather than `getNSlices()`, which is what makes a stack saved with t=30, z=1 work — that used to average nothing and analyse frame 1 alone.
- **Input images are guarded, and the image type alone is not the test.** `smFRETChannelMapper.requireGrayscale` runs at all three `run()` entry points and blocks anything that is not 8, 16 or 32 bit grayscale, because every stage assumes one number per pixel. RGB is caught by `getType()`, but a colour-indexed PNG or GIF opens through `ImagePlus` as **GRAY8, not COLOR_256** — verified against files written for the test — so 8-bit images are additionally required to have no colour lookup table. That test is deliberately not applied above 8 bits, where a colour LUT is display-only over real intensities. The cost is that an 8-bit image carrying a display LUT is refused even though its values are fine; that direction is recoverable (the message names the fix) whereas the other silently measures palette indices.
- **Everything is float, end to end, and that is where a quantization error was hiding.** Input stacks are converted once at each `run()` entry by `toFloat`, and every internal array, intermediate and output image is 32-bit from there on — `toProcessor` no longer takes a bit depth. Previously each stage rounded back into the camera's type: the averaged image to 8 bit, the warped half to 16, the background to 8. A trace is `4πσ²` times a difference of two of these, so **one ADU of rounding is 50 units of trace**. Removing it moved the dark-frame donor level — which should read zero — from **+32.7 to +12.7**, and changed 58 of 399 spots, because `MaximumFinder` no longer sees an 8-bit-quantized average. The only non-float output left is the mapping QC overlay, which is a display composite rather than data. The cost is memory: peak RSS on a 1295-frame movie went 7.0 GB → 10.1 GB, and diagnostic images are 4× on disk.
- **The medians are a selection, not a sort.** The estimate used to be rounded back into the input's type, so on an 8-bit movie the background was quantized to whole ADU — and a trace is `4πσ²` times frame-minus-background, so one ADU there is **50 units of trace**. `median()` is quickselect rather than `Arrays.sort`: it is called twice per clipping round over every trusted pixel, which was **14% of the profile** on a 1295-frame movie, and selection gives exactly the same value — verified over 4000 cases including sorted, reverse-sorted and heavily-duplicated input. Stage 3 on the long movie went from 300 s to 227 s.
- **Seeding the background clip from the previous frame was tried and rejected — it is not the same answer sooner.** Neighbouring frames' backgrounds differ by a mean of 0.035 ADU, so starting each frame from the previous level looks free, and it does cut stage 3 by a further 10% (227 s → 183 s). But the clip only ever *removes* pixels, and a seeded level is already clipped, so the first round clips harder and the iteration settles on a **different fixed point** — traces shifted by a median of 14% on the example data. That is not a rounding difference and it survives making the background float, so it is not quantization either. If it is ever revisited, the mask must not be what carries over: the clip is monotone, so an inherited mask erodes to nothing over a long movie.
- **Widen to double before subtracting.** ImageJ1's `ImageProcessor.getValue` returns a double, so arithmetic written against it was double arithmetic. Reading an imglib2 `float[]` directly and subtracting gives *float* arithmetic, which moved the traces by 1e-4 — nothing against the signal, but not nothing. The same trap cost 1 ADU on 5 pixels per million in the channel mapper's interpolation, where the fix was a `DoubleType` converter view. Anywhere ImageJ1 accumulated in double and imglib2 would accumulate in float, widen deliberately.
- **The spot finder is imglib2 except for three islands.** The arithmetic, masks, filters and background estimator are `LoopBuilder` over `RandomAccessibleInterval`, and the smoothing is `Gauss3`. What stays ImageJ1: `MaximumFinder`, whose tolerance-based flood fill has no imglib2 equivalent (`LocalExtrema` is a strict neighbourhood test); the ROI rasterizers, where `fillOval` covers 69 pixels at radius 4 against 49 for the analytic disc, so the mask footprint would change; and `ResultsTable`/`FileSaver`, which are I/O rather than pixels. The `Shared` class holds one `float[]` viewed as both an `ArrayImg` and a `FloatProcessor` so the islands run in place with no conversion.
- **`spotChannel` picks which image spots are found in, and it drags the camera black level with it.** `sum` (default, and what the plugin always did), `donor` or `acceptor`. The QC image *is* the analysis image, so the choice shows up there for free. The subtle part is `spotFilterSNR`, which subtracted `2 * cameraBlackLevel` from the background before taking its square root — correct only because the two halves had been added. It is now `channelCount() * cameraBlackLevel`, 2 for the sum and 1 otherwise; on a single channel the old factor would have over-subtracted a whole black level (5 ADU on the example data) and shifted every SNR. Verified by solving for the factor from measured SNRs at two black levels: 1.000 for donor, 2.000 for sum. **`spotThreshold` does not carry across the three settings** — a single channel has about half the background and its own signal, so the same number is a different cut. Spot positions stay in the target frame and stage 3 still measures both channels, so this changes where spots are found, not where they are measured.
- **The spot finder caches the two halves, not the image it analyses.** `buildChannelImages()` keeps the warped target and source separately and `channelImage()` composes the analysis image per run, so **changing `spotChannel` does not invalidate the cache** — comparing the same field across donor, acceptor and sum is the thing the interactive dialog is for. `channelImage()` always returns a fresh copy, including in the single-channel cases where that is only an `arraycopy`; handing back the cached half would save a fraction of a millisecond and let anything that ever wrote through it corrupt the cache.
- **`spotTolerance` is an amplitude cut wearing a noise cut's name, and it is two-sided in a way that is invisible from either end alone.** It is 5 now, not 10, swept 1–20 against ground truth at σ=1.0–3.0, two densities, 20 averaged frames, scored on survival through every filter: 5 recovers **98.3%** of the achievable recall on average and **96.0%** in the worst condition, against **79.1%/43.6%** for 10. Too high merges real spots away. Too low is worse than it looks, because `createSpotsNeighborhoodMask` is fed **`allSpots`, not the filtered set** — every noise maximum both trips the proximity filter, culling its real neighbours (at tolerance 1, σ=1, 400 spots: 6208 maxima, **3 survivors**), and masks background pixels out of `trustedPixels`, driving background rms to **44.5 ADU**. The background degrades at *both* ends: rms bottoms near tolerance 4–5 and climbs back to 0.667 by 20 as undetected spots go unmasked. It is not size-independent — the plateau's lower edge is flat at 3–4 (the noise floor) but its upper edge collapses **20 → 12 → 6 → 5 → 4** across σ=1→3, tracking a peak amplitude of `N/(2πσ²)` that falls 63.7 → 7.1 ADU — so no constant is inside every plateau, but 5 is within 4% everywhere. It also scales with the noise, hence with frame count and background: this was optimized at 20 frames because that is the usual range. On real data 10 → 5 gains 24 spots on `hel1` and 57 on `hel7`, losing 1 and 2.
- **`spotProminence` was measuring the wrong thing three different ways, and it now reads as a fraction of an isolated spot — 1.0 is a clean lone molecule at any size or brightness.** Default **0.4**, and **old values do not carry over at all**: 1.3 or 1.8 now mean "brighter than isolation allows" and reject nearly everything. What was wrong: (1) the ring ran `(srad−1)² ≤ r² ≤ (srad+1)²`, whose inner edge is 1 px at σ=1 and 5 px at σ=3, so a noiseless lone spot scored `exp(r_min²/2σ²)` = **1.649 at σ=1 rising to 4.010 at σ=3** — the old default of 1.8 sat *above* the σ=1 ideal, so **at `spotSigma` 1.0 it rejected 100% of real spots**; (2) the ring was summarised by its brightest pixel, an extreme-value statistic over 28–80 pixels and therefore mostly noise — the 90th percentile cuts the best achievable FRR+FAR from 0.830 to 0.685 averaged over σ; (3) `Math.max(1, pixelHeight)` was an absolute ADU floor, which made it **select against bright spots** — on `hel1` it dropped 52% of spots at SNR 15–25 against 16% below SNR 10, because a dim spot's ring is noise clamped to 1 while a bright spot's ring is real PSF wings. It is now a thin annulus at 2σ (`|r − 2σ| ≤ 0.6`), summarised by its 90th percentile, **minus that percentile's noise bias** (`1.2816·σ_noise`, σ_noise from the background level and `cachedFrames`) — without that subtraction the normalization does not actually equalize, and the median lone spot runs 0.90/0.64/0.70/0.66/0.47 across σ=1–3 instead of **1.02/0.92/1.07/1.04/0.77**. `idealProminence` computes its reference from the ring's own offsets with the same statistic, so geometry and reference cannot drift apart. Verified against the Python it was derived from: medians identical to three decimals. On `hel1`/`hel7` the median lands at **0.996/0.975** — the calibration holds on a real PSF, not just a Gaussian one. **Know its limits before touching it:** at a single constant threshold it does not beat keeping every spot on a clean field (a doublet closer than ~0.75σ is just a brighter point source and scores *higher* than a single); it only pays on dirty fields and mostly at σ≤2 (dirty σ=1: 95→63 errors; σ=3: no gain); and a residual anti-selection by brightness is **intrinsic, not fat wings** — it is present in simulation with an exactly Gaussian PSF (r=−0.27 at σ=2), because a dim spot's ring is unmeasurable after noise subtraction and so passes by default. **Replacing it with a shape measure was evaluated and rejected — see [ADR-0001](docs/adr/0001-no-shape-based-doublet-rejection.md), and don't re-litigate it without new numbers.** SNR-normalized ellipticity from weighted second moments is genuinely the better statistic (0.473 against prominence's 0.538 on doublets), but at a *constant* threshold it buys 5% on a clean field against 38% on a dirty one, and the two optima are far enough apart that the dirty-field setting does real damage to clean data. Two traps recorded there: raw `|e|` *loses* to prominence and only wins once divided by its 1/SNR noise floor (0.681 → 0.473), and a single-Gaussian residual χ² is 45% a brightness cut (r=+0.67 against SNR among true singles at σ=1) despite looking like the strongest aggregate detector. 0.4 is deliberately conservative: zero true singles lost in simulation up to σ=2, ~12% of detections removed on the example data. New defaults together take `hel1` 333 → 528 spots (1 lost, 196 gained) and `hel7` 246 → 462 (0 lost, 216 gained), median SNR 12.11 → 12.46 and 13.40 → 12.80.
- **Simulated spot-finding studies must hold SNR constant, not brightness, and must scale the match radius with σ.** Two methodology traps, both of which produced wrong answers first. Holding `median N` fixed while varying σ makes large-σ fields sit at the detection limit (detections 386 → 121 from σ=1 to 3), so a filter looks useless there when the field is simply too dim; `N ∝ σ` keeps true SNR flat and detections comparable (300/310/305/295/239). And `MaximumFinder` returns the integer coordinate of the brightest pixel, so localization error grows with the PSF — nearest-truth distance median 0.82 px at σ=1 against 1.26 px at σ=3, worst case 3.08 — and a fixed 1.5 px match radius scored **20% of real detections as false positives at σ=2.5**. Use `min(3, max(1.5, 1.2σ))`, capped below half the minimum truth separation so a detection can still only match one spot.
- **Mask conventions in `smFRETSpotFinder`:** `overlapMask` marks pixels inside the valid overlap region of both channels (used to drop spots near channel edges); `backgroundMask` marks pixels not within `spotMargin` of any spot, which is derived from `spotSigma` rather than being a parameter — sweeping it found anything from 2 to 6 within 11% of the best at any spot size, because the estimator clips rather than trusting the mask. Both are persisted together as a 2-frame TIF (`_spotf_masks.tif`) and reloaded via `loadMasks()`.
- **Background estimation is sigma-clipped normalized convolution.** `backgroundEstimate(image)` smooths the image and the trusted mask with the same Gaussian and divides one by the other, which fills the spots *and* the edges in one pass; then it drops pixels sitting more than a threshold of MAD-based standard deviations **above** that estimate and repeats, four rounds. The clipping is one-sided on purpose — contamination only ever brightens a pixel. There is no seeded second flavor: it converges in a fixed few rounds with nothing to carry over between frames, so `smFRETAnalyzer.backGroundEstimation()` estimates each frame independently — and reads neither `spotMargin` nor `edgeMargin`, which is why it no longer sets them on `smfsf`. It replaced an iterated Gaussian inpaint that trusted `backgroundMask` completely; on the example long movie that inpaint drove two thirds of photobleached traces significantly below zero (median −23 photoelectrons), because a real PSF's wings reach past any masking radius a crowded field can afford and the estimator read the background high exactly where it was about to be subtracted.
- **One of the three background settings follows the spot size, and it is the geometric one — the opposite of what was believed.** The **masking radius** does track it: `spotMargin` is `max(2, round(2.5 * spotSigma))`, re-swept from 2 to 10 px at σ=1.0–3.0 and two densities against a known background, scored on the bias at spot locations. The best margin runs 2, 3, 5, 8 and past 10 as σ goes 1.0 → 3.0 at 400 spots per channel. The **smoothing scale** showed no trend against sigma at all (fit 14.4 − 0.00·σ) and is a constant 14; it was `2 * spotMargin`, i.e. 8, which costs 40–60% more error than 14 at every sigma above 1. The **clipping threshold** was `1.5 − 0.3·spotSigma` and is now a constant **1.3**, re-derived against the corrected estimator by sweeping κ from 0.4 to 10 at σ=1.0–3.0 under a Gaussian beam at real density (400 randomly-placed spots per channel, log-normal brightness), scored on the bias of the estimate **at spot locations** since that is what gets subtracted from a trace. The old line was fitted while the one-sided clip still biased the level low, so it was partly compensating for the estimator rather than describing the spots; with that bias corrected the optimum is **not monotone** in σ — loose at 1.0–1.5, tightest near 2.0, back to ~1.0–1.3 by 3.0 — and no line fits it. Aggregated over σ the optimum is flat from about 1.0 to 1.6, with 1.3 best with or without σ=3 included. On `hel1` the change is invisible (background 17.441 vs 17.466, 421 spots vs 418), and 1.3 is far closer to the long movie's empirical 1.8 than the old line's 0.93. `backgroundKappa` still overrides it when set above 0.
- **`spotMargin` scales at 2.5σ, not the 3σ a PSF actually reaches, because masking is not free.** Every masked pixel is one the estimator cannot use, and at 400 spots a radius of 8 already covers most of the channel. That shows up as a real turning point: at σ=3 the error bottoms at a margin of 8 (rms 0.278) and gets *worse* by 10 (0.288) even as the bias keeps falling. Against the old fixed 4 this cuts the bias across σ=1–3 from **0.225 → 0.098 ADU at 400 spots** and 0.066 → 0.030 at 150 — worth ~15 units of trace at σ=3, systematically. A scale of 2.0 was the alternative: marginally better on a sparse field, half as good on a crowded one, and crowded is what the real data is (`hel1` carries ~430 spots per channel). On `hel1` at the default σ=2 the margin goes 4 → 5, the background falls 17.438 → 17.381, the dark-frame donor level improves −2.445 → −1.929, and the spot set barely moves (430 shared, 1 gained, 0 lost, SNR +1.5%). **It does not abolish the large-σ residual** — spot light still reaches past any radius a crowded field can afford — it just stops that residual growing unchecked with spot size.
- **The one-sided clip biases the level low, and that bias is corrected analytically — without it `spotThreshold` was not size-independent.** Keeping only pixels below `κ·spread` leaves a truncated sample, so the level reads low even where there is nothing but noise to clip: **≈1 ADU**, about 2.8× the single-round prediction because four rounds compound it. `truncationConstants(κ)` computes both terms of the fix — the mean offset `φ(κ)/Φ(κ)` *and* an unbiasing factor for the MAD, since `robustSpread` measures the spread on the already-truncated residuals and would otherwise under-correct. Constants are solved numerically (bisection on a normal CDF built from A&S 7.1.26) and **verified against scipy to six decimals**, with both limits correct: at κ=8 the offset is 0 and the MAD factor 1. **The level is corrected inside the loop, not once at the end** — that keeps each round's clip in the right place and is what stops the bias compounding. Cost is one add per pixel per round with the constants cached per κ; unmeasurable.
- **Trace intensities were half their true value until the norm was fixed, so absolute intensities from before that commit are not comparable.** `measureTimeTraces` smooths with a *normalized* Gaussian, which leaves `N / (2π(σₛ² + σₐ²))` at the centre of a spot carrying `N` photons — the widths add in quadrature. The norm was `2πσ²`, the factor that turns a normalized Gaussian into a unit-height one; that is the right correction for the kernel but leaves the spot's own width out of the quadrature sum, so it recovered only **N/2**. It is now `4πσ²`. Verified against simulated movies with a known integrated intensity, matched `spotSigma`, σ=1.0–3.0: recovery went **0.480–0.495 → 0.960–0.990**. The residual shortfall is understood and is not in this factor — at σ≤2 it is exactly pixel integration (`1/(1+1/24σ²)` predicts 0.9600 at σ=1 against 0.9604 measured), and about half of the larger σ=3 deficit is spot light leaking into the global background estimate, which falls away as the field gets sparser (0.965 at 105 spots → 0.984 at 32, then flat). **FRET ratios are unaffected**, since a common factor cancels out of `A/(D+A)` — only absolute intensities move. `spotFilterSNR` carried the identical error and was fixed with it, which has a bigger consequence: **every reported SNR is √2 larger than before** (verified at 1.41421 across σ=1–3), so the same `spotThreshold` now admits more spots — 354 → 418 on `hel1`. The number it reports is now the true matched-filter significance, `N/(2σ√(πB))`, rather than that over √2, so **`spotThreshold` reads in real sigma: 6 means 6σ where it used to mean 8.49σ.** Thresholds carried over from before this commit should be multiplied by √2 to keep their old selectivity.
- **`spotThreshold` was silently size-dependent, and the mechanism is worth understanding before touching the SNR code.** Verified on simulated sparse movies, σ=1.0–3.0, analysed at the matching `spotSigma`, 105 spots each, against ground truth. At **constant true significance** the reported SNR drifted **+15%** from σ=1 to σ=3; at **constant molecular brightness** — the physically real case, since a fluorophore emits the same photons whatever the PSF width — it drifted **+46%** (0.99 → 1.45). Two causes, roughly half each. First, `spotFilterSNR` converts a per-pixel background error into an integrated one by multiplying by `norm` (now `4πσ²`), while the signal `N/2` grows only as σ, so **any constant background bias produces an SNR error proportional to σ**. Second, `clippingThreshold()` tightens κ from 1.2 to 0.6 across that range, deepening the clip bias from 0.63 to 1.43 ADU and compounding the first. Pinning κ cut the drift from 15.4% to 7.2%; the truncation correction takes it to **0.5%**, and the fixed-brightness spread from 46% to 4.6%. The practical symptom was a threshold that half-worked: at σ=3 a true-SNR-4.0 spot reported 5.77 and 5 of 105 slipped past `spotThreshold=6`, with false positives climbing monotonically with σ. Corrected, it reports 3.74 and none pass. **The correction costs spots on real data** — 399 → 354 on `hel1`, 496 → 482 on `hel7` — because those spots only ever passed on inflated SNR.
- **The example movies do not photobleach, and the short ones must not be used to judge background estimation.** The drop to near-zero at the end of `hel1` is **the illumination laser being switched off for a few frames**, not photobleaching — which is why the dark-frame donor level is a valid zero-reference at all (no illumination, so no signal, so it must read zero). But on a 30-frame movie with `backgroundAverageNFrames=30` the temporal window spans that switch-off, so the background estimate is contaminated by the illuminated frames: the median trace dips to **−62.7** at frame 15 before settling. Treat the dark-frame level on `hel1` as indicative, never decisive; the primary evidence for background work is simulation with a known answer. `hel7` is worse for this purpose in a different way — **only 29% of its traces ever fall below 20% of their starting level**, its median trace ends at 138 having peaked at 264, so its "dark-frame" number is mostly un-bleached signal and means nothing at all.
- **The background estimate is smoothed on a grid decimated by 4, and that beat every library alternative that was tried.** The σ=14 smoothing was ~70% of stage 3, so `maskedSmooth` now bins by `backgroundDecimation`, blurs at σ/4 on the coarse grid, and interpolates back. Stage 3 on the 1295-frame movie went **209 s → 103 s**; the estimate moved by an rms of 0.02 ADU on a level of 16, **no spot moved on either test movie**, and traces shifted by a median of 0.16% — against the 2.9% that removing the 8-bit quantization moved them. D=8 was rejected: 9 s more for a changed spot set (496 → 495, 2 lost and 1 gained). **The tie to `backgroundSmoothing` is load-bearing and invisible from either constant alone** — binning is a box prefilter adding `D²/12` to the kernel variance, negligible at 1.3 against σ=14's 196 but 11% if σ were dropped to 3.5, so keep `backgroundSmoothing / backgroundDecimation ≥ 3.5`. Only the background smoothing is decimated; `spotSigma` is untouched.
- **Three faster convolutions were measured and all three lost — don't re-litigate this without new numbers.** Per masked-smooth at σ=14 on 256×512: decimate D=4 **2.12 ms**, `FastGauss` 3.70 ms, `Gauss3` (current, full-res) 6.65 ms, imglib2-algorithm-fft **13.80 ms**, imagej-ops `PadAndConvolveFFT` **29.40 ms**. Both FFT paths are numerically *exact* against `Gauss3` (rms 0.00000, max 2e-5 ADU) and identical to each other, so the 2.1× between them is pure overhead — ops re-transforms the kernel and re-pads on every call, where a hand-rolled path hoists the kernel transform out entirely (the kernel is the same σ=14 Gaussian on all 12,955 smooths). **FFT does not overtake direct convolution here until about σ=40**, because padding inflates 256×512 to 360×630 and JTransforms' complex arithmetic carries a far larger constant than a separable real convolution; at σ=56 imglib2 FFT finally wins, 32 ms against 50 ms. `net.imglib2.algorithm.convolution.fast_gauss.FastGauss` is *not* σ-independent as an IIR filter should be (1.65/1.78/1.54/3.53 ms at σ=2/7/14/28) because imglib2's implementation carries a border proportional to σ, and D=2 beats it on **both** speed and accuracy. `imglib2-algorithm-fft` was added to `pom.xml` for this test and removed again; nothing in `src/main` uses FFT.
- **`Gauss3` is a direct separable convolution — no FFT, kernel truncated at ±3σ.** `halfkernelsizes` returns `ceil(3σ)+1`, so the full width is ~6σ+1 and cost is pixels × σ, measured flat at 0.10 ns per tap-pixel from σ=7 to σ=28. Two consequences: decimation works because *both* factors shrink together (hence D³ on the blur alone), and it stops paying by D=4 because below σ≈3.5 the per-tap cost triples as imglib2's per-call dispatch overhead swamps the convolution. Above σ≈56 the kernel exceeds the row length and direct convolution degrades badly (0.286 ns/tap) — that is where the FFT calculus would change.
- **The upsampler is hand-rolled because no library one exists that isn't slower.** Every candidate — imagej-ops `DefaultScaleView`, `Scale2D` + `RealViews`, and imglib2's own `NLinearInterpolatorFactory` — resolves to a per-pixel `RealRandomAccess`: a `setPosition` and a `get()` each, measured at **4.8 ms** on a 256×512 frame, *more than the full-resolution σ=14 blur the decimation exists to avoid*. The first version of this used exactly that and made stage 3 **slower** (209 s → 402 s at D=4), which is what the separable bilinear in `unbin` replaced — 0.3 ms, same answer to four decimals. The optimized library downsamplers (`blocks.downsample.Downsample`, `ScaleAreaAveraging2d`) only address `bin`, which was never the expensive phase.
- **Spot arrays are `double[][]` shaped `[spot][field]`, and there are two incompatible layouts — check which one you're holding.**
  - *In memory during spot finding:* column 0 is a boolean-as-double "is this spot still good" flag written by each filter stage (`spotFilterWithMask`, `spotFilterSNR`, `spotFilterProminence`), so x/y live at columns 1/2. `getMaxima` returns width 3 (`flag, x, y`); `spotFilterSNR` appends SNR (width 4); `spotFilterProminence` appends prominence (width 5). Filters append a diagnostic column rather than overwriting existing ones.
  - *After a save/load round-trip:* the flag is gone. `saveSpotLocations` writes only good spots starting from index `j+1`, and `loadSpotLocations` reads back into index `j`, so the reloaded array is `x, y, snr, prominence` with **x at column 0** (matching `columnHeaders`).
  - `smFRETAnalyzer` only ever sees the reloaded form — hence `spots[j][0]`/`spots[j][1]` as x/y in `measureTimeTraces` — while everything inside `smFRETSpotFinder` uses the flag-prefixed form. The round trip only lines up because exactly two widening filters run and `columnHeaders.size() == 4`; adding a filter stage means updating `columnHeaders` in lockstep.
- **JSON as the inter-plugin contract.** Jackson `ObjectMapper` reads/writes plain `Map<String,Object>` (via `HashMap.class`), not typed DTOs. Downstream plugins read specific keys by string (e.g. `smFRETAnalyzer.run()` pulls `"root name"`, `"image name"`, `"mapping file"`, `"masks file"`, `"spots file"`, `"spot sigma"`, `"camera black"`, `"camera gain"` out of the spot-finder JSON) and must stay in sync with the keys the upstream plugin writes.
- **`smFRETSpotFinder` is `Interactive`, and its dialog outlives a run.** It implements `org.scijava.command.Interactive`, which makes SciJava render the same `@Parameter` declarations as a **non-modal** dialog instead of a modal one — no hand-written Swing, no change to the widgets or the `min` validation, only to the dialog's lifetime. A `org.scijava.widget.Button` parameter with `callback = "findSpots"` is what actually triggers an analysis; running on every parameter change would re-analyse and rewrite four output files while a number was being typed. **Opening the dialog analyses nothing** — SciJava runs an Interactive command once as it opens, which defeats the point of setting parameters up first, so `run()` analyses only when `isHeadless` or `ij.Macro.getOptions() != null`. That second test is what keeps the batch macros working: they drive this as `run("smFRET Spot Finder", "inputimagename=... spotthreshold=...")` and have no button to press. Note `Macro.getOptions()` returns null unless the calling thread is named `Run$_…`, which is how ImageJ1 names macro threads — so a test that calls it on the main thread will wrongly conclude the macro path is broken. `findSpots()` also returns quietly when the two file parameters are unset, since an interactive dialog exists before its inputs do. Every run still writes all four outputs, so the contract with stage 3 is unchanged.
- **The spot finder caches everything up to the summed image, keyed on four inputs.** Loading, the temporal average, the split and the warp depend only on `inputImageName`, `mappingFile`, `startSlice` and `endSlice` — not on any parameter worth tuning — and they are most of the cost of a run. `buildSumImage()` keeps the result and rebuilds only when that key changes. **`startSlice`/`endSlice` are in the key because they choose which frames get averaged**, so changing either has to redo the whole prefix; verified by driving one instance through parameter changes and comparing every result against a cold instance, byte for byte. Only one QC window is used too, updated in place, since otherwise each adjustment would leave a window behind.
- **Menu registration is deliberately doubled.** Each command carries a SciJava `@Plugin(menu = {@Menu(...)})` declaration *and* an entry in `src/main/resources/plugins.config`. The annotations alone place the `smFRET` submenu in the trailing section of Fiji's Plugins menu (after the separator that follows `Volume Viewer`), because that is where `imagej-legacy` appends ImageJ2 commands — and no `@Menu` weight can move it across that separator (verified empirically). The `plugins.config` entries put it in the main plugins section instead. Consequences: **in Fiji the order of lines in `plugins.config` determines the order of items inside the submenu, and the `@Menu` weights do not** — they only apply where the legacy layer isn't involved. The listed classes are `Command`s rather than `ij.plugin.PlugIn`s; Fiji's legacy patcher dispatches them into the SciJava command service regardless, so parameter dialogs still work.
- **TurboReg measures mappings; imglib2 applies them.** TurboReg is called via reflection (`IJ.runPlugIn("TurboReg_", options)` + `getClass().getMethod(...)`) because it isn't a compile-time Maven dependency — it must be installed separately into the Fiji/ImageJ plugins directory at runtime. It is used for **`-align` only**, in `smFRETChannelMapper.run()`, which is the one thing it does that nothing else here can: fit an affine to two images. Applying a known affine is `transformImagePlus`, which solves the affine from the three landmark pairs in `loadMappingJSON` into an `AffineTransform2D` and samples an `NLinearInterpolator` in memory — no temp file, no reflection, and testable without a Fiji install. It runs once per frame per channel from both `smFRETAnalyzer` stages, so it is the hot path; TurboReg's `-transform` took 6.9 ms on 256×512 against 1.4 ms here, and only 0.5 ms of that was the temporary file.
- **The warp is n-linear where TurboReg's was a cubic spline, and that is fine — measured, not assumed.** On the example mapping and data: geometry agrees to 0.003 px of spot centroid (the affine is exactly determined by three point pairs, so this is arithmetic, not luck); stored 16-bit values differ for 14% of pixels, 14.17% of them by exactly 1 ADU and 0.12% by ≥2; per-spot intensities after the smoothing that precedes trace measurement differ by a median of 0.45% (p95 0.75%). The decisive number is that rounding into 16 bit at the end of `transformImagePlus` has an rms error of 0.26 ADU against 0.24 ADU between the two interpolators — **storing the image perturbs it more than the choice of interpolator does**. Higher-order interpolation is not worth buying back: imglib2 Lanczos halves the pixel-level difference but is no closer on per-spot intensity, because the σ=2 smoothing discards the difference, and it is 6× slower than TurboReg. Two details are load-bearing and were each worth a measurement: the out-of-range test is on the **inverse-mapped coordinate** rather than the sampled value, which is what `createOverlapMask` relies on and what keeps a 3 px band around the frame from shifting by up to 19 ADU; and the interpolation runs through a `DoubleType` view because ImageJ1 interpolated in double, and matching that is worth 1 ADU on ~5 pixels per million.
- **Diagnostic mode:** each class has a `private final boolean diagnostic_mode = true` field controlling whether intermediate images (averages, smoothed foreground/background, per-frame background stacks) are written to disk alongside the primary outputs. There's no CLI flag for this — toggle the field directly when debugging.
- Exceptions specific to this plugin's own validation (e.g. image-size mismatches against a loaded mapping) are raised as `smFRETAnalysisException` (unchecked). Everything else is caught broadly in each `run()` and routed to `log.info(e)` + `IJ.handleException(e)` rather than propagated, since these are top-level SciJava commands.

## Build

Maven build against the `pom-scijava` BOM/parent, **which must run on a JDK that can still emit Java 8 bytecode**:

```
JAVA_HOME=/usr/lib/jvm/java-11-openjdk-amd64 mvn clean package
```

`pom-scijava` sets `maven.compiler.release` to 8 (matching the Java 8 runtime Fiji bundles — `Fiji.app/java/zulu8*`), and the JDK 21 compiler rejects `--release 8` with `error: release version 8 not supported`. Plain `mvn clean package` therefore fails on a machine whose default `java` is 21: `maven-compiler-plugin` compiles in-process using the compiler of whichever JVM Maven itself is running on, so it is `JAVA_HOME`/`java` that decides, **not** the `javac` on `PATH` — a PATH `javac` of 11 does not rescue the build. `mvn -version` reports the JVM actually in use. Add `-o` to build offline once the dependencies are in `~/.m2`.

The build resolves ImageJ/SciJava core artifacts from Maven Central plus the `scijava.public` repository declared in `pom.xml`. There is no test suite in this repository (no `src/test`), so `mvn test`/`mvn verify` runs no tests.

**Runtime dependency not in `pom.xml`:** the channel mapper requires the [TurboReg](https://imagej.net/plugins/turboreg) plugin (v2.0.1) to be present in the target Fiji/ImageJ installation's plugin path — it's invoked via reflection at runtime, not linked at compile time.

To use the plugin, install the built jar into a Fiji/ImageJ `plugins/` directory alongside TurboReg; the four commands then appear under `Plugins > smFRET`.
